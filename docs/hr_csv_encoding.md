# HR求人CSVの文字欠落とWindows拡張文字の読込

2026-10-16。本文・識別子・接続先・認証情報は記録せず、件数と文字の種類だけを残す。

## 生bytesの切り分け

保存済みCSVを探索したが見つからなかったため、既存の `hr_csv_fetcher.fetch_hr_csv` で公開求人のCSVを1本取得した。求人編集画面へのアクセス、別形式の出力実験、HubSpotへの書込みは行っていない。取得物と認証状態はGit対象外の `scratchpad/`、ログは作業ディレクトリ配下に保存した。

対象はCSV内で公開状態の1,603件。依頼時に確認された40件の集合との照合は行っておらず、その内訳としては扱わない。取得処理は既存の完了済みエクスポートを選び得るため、編集画面の現時点の値との同時性は保証しない。

| 分類 | 求人数 | 文字数 | 判断 |
| --- | ---: | ---: | --- |
| (a) 本文に生の疑問符 0x3F がある | 445 | 6,919 | デコード前から存在。通常の疑問符も含む欠落候補の上限であり、全てを文字欠落と断定しない |
| (b) cp932で読めるがShift_JISでは置換文字になる | 0 | 0 | 今回のCSVに復元対象のWindows拡張バイトは無かった |
| 両デコーダのUnicode対応が異なる | 929 | 6,956 | 波線6,823文字（929件）、全角ハイフン133文字（15件）。求人数は重複あり。これは疑問符への欠落とは区別する |
| cp932でも読めない本文bytes | 0 | 0 | 今回はcp932で全体を読めた |

本文は取込と同じ列集合・整形で集計した。生ファイル全体の0x3Fは6,923バイトであり、本文外の4バイトは本文件数に含めていない。UTF-8 BOMは無く、UTF-8の厳密デコードは失敗、cp932の厳密デコードは成功した。Shift_JISの `errors="replace"` が生成するのはU+FFFDであり、ASCIIの疑問符ではない。CSVに既に0x3Fがあれば、読込変更では元の文字を復元できない。

文字の種類ごとの扱い:

- 丸数字などのWindows拡張文字: cp932に表現可能。対応bytesが残っているCSVなら今回の修正で保持できる。今回のCSVには対応bytesが無く、実データでの復元件数は0。架空のbytesで読込を検証した。
- 通常の罫線（一重罫線など）・通常の漢字: cp932で保持できる。元からShift_JISでも読めるものもあるため、全てが今回新たに直る文字ではない。
- 康熙部首（人・支・田に似たUnicode部首）・二重罫線U+2550: cp932にも表現が無い。出力時に疑問符に置換されると復元不能。
- 波線・全角ハイフン: cp932とShift_JISで同じbytesから得るUnicode文字が違う。今回の集計では置換文字の発生とは分けて数えた。

疑問符になったbytesには元の文字の情報が残らない。康熙部首・丸数字・二重罫線それぞれに由来する疑問符の確定件数はCSV単独では算出不能。依頼時の編集画面との比較結果（40件中15件に疑問符）と、今回の全公開求人CSVの445件を混同しない。

件数だけの再確認:

```sh
python -m scripts.job_application_sync.hr_csv_encoding_check scratchpad/csv_fetched/hr/対象.csv
```

このコマンドはローカルファイルを読むだけで、本文・求人ID・パスを出力しない。欠落候補、旧デコーダだけの置換、Unicode対応差を別々に数える。

## 読込と差分監視

取込・店舗逆引き・backfill・health用の読込を共通の `HR_CSV_ENCODING = "cp932"` と `errors="replace"` に統一した。不正bytesで途中終了させない。

監視スナップショットには `csv_encoding` と、同じ元bytesを旧デコーダで読んだ比較用ハッシュを加えた。cp932には同じ文字を表す別のbytesがあるため、再エンコードによる推定だけには頼らない。移行前の控えに限り、旧Shift_JIS置換結果、またはShift_JIS非対応文字だけを疑問符にした結果との一致を認める。疑問符を任意の文字に一致させる比較は行わない。本文と画像を合わせたハッシュ、タイトル、公開状態の全てを確認するため、別の編集があれば従来どおり変更になる。

差分0件でも新しい控えを保存する既存の処理により、次回からはcp932の厳密な指紋比較へ移る。旧控えに本文指紋が無い場合は、従来どおり初回の版を作る。不正bytes由来のU+FFFDは移行例外にしない。

旧値が既に疑問符になった位置の元の文字は証明できないため、同じ日にWindows拡張文字自体が編集されていた場合に、その編集を一度だけ区別できない余地は残る。移行前の控えだけに限定して影響を抑える。

監視で変更として数えないだけの移行では、その日その求人のHubSpot本文が即座に書き換わる保証はない。必要なら既存の `--copy-only` を **dry-runで確認**し、別途運用判断で一回だけ読込修正として反映する。今回HubSpotへの反映は実行していない。実行する場合はHubSpotに本文の版が一つ残る。

## 別形式の出力と残る欠落の検知案

既存コード・リポジトリ内ドキュメントを確認した。出力操作は `is_valid` による状態絞込みと `csv-download=1`、生成完了後の `download-csv` リンク取得で、文字コードを切り替える引数やUTF-8選択肢の記録は見つからなかった。管理画面の全選択肢を網羅した保存資料は無く、UTF-8出力が存在しないとまでは断定しない。新しい引数の試行や画面探索はしていない。

health_checkへの追加案（提案のみ）:

- HubSpotの本文について、疑問符を含む求人数・疑問符数・U+FFFDを含む求人数を集計する。本文・ID・顧客名は公開ログに出さない。
- 同じ取得範囲・時点のCSV診断件数と併記し、欠落の「疑い」として表示する。疑問符は通常の文章にもあるため、確定エラーとは扱わない。
- 元文字の確定・復元が必要な場合のみ、編集画面の値との比較を検討する。ページ単位の取得による負荷、SSO・セッション失効・再認証の制約があり、全求人を毎回巡回する設計は避ける。今回この補完は実装・実行していない。

## 検証

架空のcp932 bytesで、丸数字・罫線・漢字、不正bytes、旧値の疑問符／U+FFFDからの移行、通常の本文・画像・タイトル・公開状態の変更、件数のみの診断をテストした。

全テスト807件が成功（既存の非推奨警告1件）。

リポジトリにはlintコマンドの定義が無いため、Ruffを `--isolated --select E9,F63,F7,F82` で全体に実行する。既存の型注釈に不足していた `Iterable` のimportを補い、この検査も通す。
